About

I learn by getting close to the problem.

I've never been satisfied knowing only the part of a system assigned to me. If I'm using a tool, a sensor or a model, I want to know what it's doing, where it fails and how it fits into everything around it. That instinct has taken me across a wide range: Arduino circuits, computer vision, enterprise backends, native iOS and multi‑agent AI systems.

My path started with physical computing, debugging with a multimeter as often as a terminal. Computer engineering gave me the software foundations. At TCS and LTM the code sat inside larger operational workflows, so correctness and reliability mattered. At USC I've gone deeper into machine learning, data mining and language systems.

FitandFine brings those threads together: a product shaped by something I care about personally, where I own the interface, the backend, the data model, the OCR pipeline and the AI layer at once. That kind of ownership forces me to think about the user and the architecture at the same time, and it's the work I want to keep doing.

01

I build to understand

Documentation is a starting point. A working prototype tells me what the real problem is. I get something running early, inspect each layer and improve it with evidence.

02

I think in complete systems

A model is only useful if the data reaches it reliably and the result makes sense to a person. I care about the whole path from input to interface.

03

I care about the unglamorous parts

Caching, validation, error states, background jobs and offline behaviour decide whether a demo becomes a dependable product. I enjoy that work.

04

I ask questions early

I'm comfortable owning a problem, but independence isn't silence. I clarify assumptions, share progress and surface risks before they get expensive.
