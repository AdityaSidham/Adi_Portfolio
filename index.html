I've never been satisfied knowing only the part of a system assigned to me. If I'm using a tool, a sensor or a model, I want to know what it's doing, where it fails and how it fits into everything around it. That instinct has taken me through Arduino circuits, computer vision, enterprise backends, native iOS and multi-agent AI.

I started in physical computing, debugging with a multimeter as often as a terminal. Computer engineering gave me the software foundations. At TCS and LTM my code sat inside larger operational workflows, so correctness and reliability mattered. At USC I've gone deeper into machine learning, data mining and language systems.

FitandFine brings those threads together. I own the interface, the backend, the data model, the OCR pipeline and the AI layer at once, which forces me to think about the user and the architecture at the same time. That's the work I want to keep doing.

I build to understand

Documentation is a starting point. A working prototype tells me what the real problem is, so I get something running early and improve it with evidence.

I think in complete systems

A model only helps if the data reaches it reliably and the result makes sense to a person. I care about the whole path from input to interface.

I like the unglamorous parts

Caching, validation, error states, background jobs and offline behavior decide whether a demo becomes something people can depend on.

I ask questions early

Owning a problem doesn't mean going quiet. I check assumptions, share progress and raise risks before they get expensive.
